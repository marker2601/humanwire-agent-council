# HumanWire agent-persona runtime design

**Date:** 2026-08-14
**Status:** Approved design with live-progress amendment; implementation pending
**Proof class:** Synthetic agent simulation only

## Objective

Add an optional agent-in-the-middle persona runtime and loopback-only live-progress viewer to HumanWire's existing synthetic proof. Fictional stakeholder agents will independently decide how to respond to HumanWire deliveries, while the existing orchestrator retains all authority over identity, transport envelopes, persistence, workflow state, and public projection.

The runtime must make the simulation feel realistic and repeatable without representing synthetic actors as humans or fake transport as live Caspian, email, or Telegram proof.

## Existing foundation

HumanWire already provides the required authoritative boundaries:

- six explicit deterministic persona strategies;
- strict Pydantic scenario, action, transcript, and provenance models;
- fresh file-backed SQLite for each generated or replayed run;
- one injected `OfflineCaspianClient` and one real `CaspianGateway` handler;
- orchestrator-owned sender, route, conversation, connection, message, and token identity;
- deterministic virtual time, transcript digest, semantic trace hash, and frozen replay;
- private-safe Decision Room, Reach, Data, JSON, CSV, and ICS projections;
- an existing OpenAI-compatible `FeatherlessJsonClient` with bounded JSON-only output.

The new runtime extends the persona decision boundary only. It does not replace HumanWire's workflow, repository, gateway, state machines, or replay implementation.

## Framework decision

### Primary: existing HumanWire client and Pydantic models

The primary implementation will use the existing `FeatherlessJsonClient` behind a small persona decision protocol. This is the fastest and smallest fit because HumanWire already has provider configuration, safe error normalization, Pydantic validation, deterministic fallbacks, and complete orchestration.

No new agent framework will be added merely to reproduce state, routing, persistence, or replay that HumanWire already owns.

### Bounded fallback: PydanticAI Slim

If the direct adapter cannot reliably enforce the strict persona output contract without framework-like retry or structured-output machinery, the fallback is [`pydantic-ai-slim`](https://github.com/pydantic/pydantic-ai) with only its OpenAI-compatible provider integration. It may implement the persona decision protocol, but it may not become the workflow orchestrator or gain repository, filesystem, transport, or tool access.

### Rejected for this scope

- [LangGraph](https://github.com/langchain-ai/langgraph) and [Microsoft Agent Framework](https://github.com/microsoft/agent-framework) provide durable, stateful orchestration that would duplicate HumanWire's existing state machines, persistence, restart recovery, and human-authority rules.
- [CrewAI](https://github.com/crewAIInc/crewAI) provides role-oriented multi-agent orchestration but would likewise duplicate the existing orchestrator and make deterministic authority harder to audit.
- [AutoGen](https://github.com/microsoft/autogen) is not selected because its official repository marks it as maintenance-only for new work and directs new users to Microsoft Agent Framework.

## Persona identities

Each generation preserves the existing nine-person scenario shape while assigning seeded fictional display identities:

1. one synthetic manager;
2. one `INFORM` persona;
3. one `ACKNOWLEDGE` persona;
4. two independent `QUICK_RESPONSE` personas;
5. one `STRUCTURED_INTERVIEW` persona;
6. one `REVIEW_APPROVAL` persona;
7. one `AVAILABILITY` persona; and
8. one separate `CHANGE` authority for the independent partial/no-meeting story.

Stable internal persona IDs and contract roles do not change. Display names are chosen from a committed fictional-name catalog using an explicit seed. The same seed produces byte-identical persona identities and ordering. Every email uses the reserved `.example.test` domain; every Telegram address and conversation is synthetic and generated by the orchestrator. No generated identity may be written to the private live directory.

The transcript records the seed and generator version. A change to the seed, persona facts, or actions changes the transcript digest and semantic trace hash.

## Isolation boundary

The persona decision engine receives one immutable, sanitized context containing only:

- its role and engagement contract;
- bounded fictional private facts;
- its allowed intent set;
- the current HumanWire delivery text;
- its own inbox and transcript;
- virtual time.

It must never receive or retain:

- another persona's transcript or facts;
- database, repository, workflow, event-log, or expected-final-state access;
- real or synthetic route, sender, destination, conversation, connection, message, token, or assignment identifiers;
- credentials, ambient environment, filesystem, browser, shell, network, or arbitrary tools.

Only a centralized model adapter may perform an explicit Featherless request in model-assisted generation mode. Persona objects themselves receive no network client or tools.

## Output contract

Each decision is a strict Pydantic object with extra fields forbidden:

- one allowed intent such as `silence`, `ack`, `answer`, `confirm`, `approve`, `change`, `available`, or a bounded proposal response;
- bounded fictional content when the intent requires it;
- a non-negative virtual delay within the scenario limit;
- optional visibility constrained to the approved enum.

The persona cannot choose sender identity, route, channel envelope, message identity, success state, or workflow transition. The orchestrator validates the response, translates its typed intent into existing HumanWire wire text, attaches fixture-owned envelope identity, and re-injects it through the single fake-Caspian handler.

An invalid, disallowed, late, or timed-out response becomes a recorded synthetic error or silence. It never becomes a guessed approval, confirmation, answer, or availability statement.

## Data flow

```text
HumanWire delivery
  -> orchestrator selects exact synthetic persona
  -> sanitized persona-only context
  -> deterministic policy or optional model decision engine
  -> strict response validation
  -> orchestrator-owned identity and wire translation
  -> OfflineCaspianClient.emit_inbound(...)
  -> existing single CaspianGateway handler
  -> unchanged workflow and repository
  -> safe projection and frozen replay
```

Every non-silence persona action must correspond to exactly one captured gateway inbound attempt. Direct calls to `workflow.handle` and direct repository mutation remain prohibited.

## Live-progress viewer

An explicit local/private CLI option may start a viewer bound only to `127.0.0.1`. Starting a simulation remains a CLI action; the viewer has no POST route, command tool, model tool, provider credential, or workflow mutation capability.

The generation process publishes an allowlisted progress snapshot after each persisted causal step. A snapshot contains only replay-safe presentation fields:

- run alias, scenario label, mode, and synthetic provenance;
- current persisted event ordinal and total saved event count;
- safe source, destination, generated-result, phase, status, and data-point labels;
- selected synthetic persona label and contract;
- safe aggregate counts and completion/failure state;
- the final semantic trace hash only after completion.

It must not contain raw persona facts, prompts, answers, routes, addresses, destinations, conversation/connection/message/assignment IDs, credentials, provider bodies, database coordinates, filesystem paths, UUIDs, or model diagnostics.

The local viewer polls this safe snapshot and supports two states:

1. **Follow live:** automatically follows the newest persisted step, visibly updates `From -> To -> Generated`, highlights exactly one affected persona or the origin, and describes the data point saved at that stage.
2. **Replay:** after at least one event exists, the operator can pause following, select any saved event, or use Previous, Next, Play, and Pause. After completion, the same controls replay the complete frozen story from Event 1.

The UI never displays a predicted next step as completed. Waiting for an agent, model timeout, synthetic silence, workflow rejection, and terminal failure are distinct truthful states. If the viewer joins late, it receives the full safe saved-event snapshot and can immediately replay from the beginning.

Motion is limited to highlighting and short opacity/position transitions. It respects `prefers-reduced-motion`, stops playback while the page is hidden, uses at least 14-pixel meaningful text and 44-by-44-pixel controls, and preserves keyboard/focus/live-region behavior.

The final JSON evidence control is enabled only when generation completes and must return an attachment with `Content-Disposition`; it must not navigate the browser to raw JSON. CSV remains a download. In-progress progress JSON is an internal local polling representation, not a submission artifact.

## Scheduling and concurrency

The virtual-clock priority queue remains authoritative. Decisions for distinct personas may be evaluated concurrently only when their triggering deliveries are already persisted at the same causal boundary and neither decision depends on the other.

Results are committed to the synthetic queue in deterministic order using virtual time, persona order, trigger identity, and action ordinal. There is at most one in-flight decision per persona. Concurrency may reduce model latency but may not change transcript ordering or state outcomes.

Replay never calls a model or constructs a persona policy. It validates the frozen transcript and injects its saved actions in their canonical order.

## Modes and provenance

### Deterministic generation

Uses the existing deterministic policies, an explicit seed, fake Caspian, and fresh SQLite. It remains the release and CI path.

### Model-assisted generation

Uses the same isolated contexts and strict output contract but permits the centralized Featherless adapter to choose persona responses. It is exploratory and may be frozen after validation. It is never a deterministic release gate.

### Frozen replay

Uses a validated transcript only, makes no model/provider call, and must reproduce the saved semantic trace from a new run root.

All artifacts and UI generated from these modes retain the six exact synthetic labels:

- `proof_class=synthetic_multi_persona`
- `actor_type=simulated_persona`
- `identity_source=synthetic_fixture`
- `transport=fake_caspian`
- `human_attested=false`
- `live_provider_verified=false`

Model-assisted generation additionally records its mode, model identifier, prompt/schema version, seed, and transcript hash in the private provenance sidecar. It does not expose prompts, private facts, provider bodies, or credentials in public projections.

Both deterministic and model-assisted generation may use the loopback viewer. Viewer state is derived from already-persisted synthetic steps; closing or refreshing the viewer cannot alter generation.

## Public and private deployment boundary

The public Vercel demo remains GET-only, read-only, deterministic, and backed by frozen synthetic data. A visitor cannot start a model run, write the public database, trigger a provider message, or access the loopback progress surface.

Model-assisted generation runs only through an explicit local/private CLI command with a new atomic run root. The optional viewer refuses non-loopback binding. Generated output may be reviewed, privacy-scanned, frozen, and then used as a read-only replay fixture.

The private Supabase/Caspian sandbox remains separate. Synthetic identities and agent decisions must never be inserted into its live directory or represented as consenting test identities. Real-provider proof still requires real operator-owned channel accounts and remains pending until its independent checklist passes.

## Failure handling

- Missing model key: use deterministic mode or fail the explicit model-assisted command safely.
- Timeout, HTTP error, invalid JSON, or schema mismatch: record safe reason only and convert the persona outcome to synthetic silence/error.
- Intent outside the persona allowlist: reject without gateway injection.
- Duplicate trigger: append a visible replay attempt but do not create a second workflow effect.
- Ambiguous persona or trigger identity: fail closed before injection.
- Model content containing routes, credentials, commands, or extra fields: reject at validation and privacy boundaries.
- Model drift: freeze only transcripts that pass all semantic, privacy, and replay checks.
- Progress publication failure: generation remains authoritative, the viewer shows a safe unavailable/stale state, and no workflow step is retried merely to update presentation.
- Viewer disconnect or refresh: resume from the complete safe snapshot without changing the synthetic run.

## Verification

Implementation is complete only when tests prove:

1. seeded fictional identities are stable, distinct, `.example.test`-only, and absent from the private live directory;
2. each decision engine can access only the approved context fields;
3. model responses cannot forge envelope identity or authority;
4. each of the six persona contracts produces valid typed behavior;
5. invalid output, timeout, and provider failure become silence/error and never advance authority;
6. safe independent decisions may execute concurrently while canonical ordering remains byte-identical;
7. generated transcripts validate, freeze, and replay without invoking a model;
8. deterministic generation and replay preserve the expected `meeting_ready` plus separate `partial` stories;
9. public projections contain the exact synthetic labels and no private facts, credentials, routes, UUIDs, or provider bodies;
10. a mid-run viewer shows only persisted events, follows new steps in exact order, and can switch between Follow live and manual replay;
11. Play/Pause/Previous/Next preserve `From -> To -> Generated`, one-card highlighting, descriptions, live copy, reduced-motion behavior, and hidden-page pause;
12. completed JSON uses attachment download semantics, and partial polling data is not exposed as a submission export;
13. the viewer is loopback-only, GET-only, and unable to mutate generation, workflow, repository, providers, or the public demo; and
14. the private live organization, Supabase data, public deployment configuration, and existing smoke output remain unchanged.

The focused synthetic, gateway, workflow, web, privacy, lint, and full-repository gates must pass before a fixture or public replay is updated.

## Non-goals

- live Caspian, email, Telegram, Featherless, or real-human proof;
- autonomous access to tools, browsers, shells, repositories, files, or production systems;
- replacing HumanWire's workflow with a general-purpose agent framework;
- making the public demo stateful or writable;
- exposing a remotely writable or publicly hosted simulation runner;
- claiming that a randomized persona has consented, approved, or exercised organizational authority.

## Success criteria

The result is a convincing agent-in-the-middle simulation whose stakeholders behave independently, whose persisted causal flow can be watched while it develops and replayed afterward, and whose evidence remains deterministic and auditable. It must be faster to implement and operate than adopting a general orchestration framework, while retaining PydanticAI Slim as a bounded compatibility fallback rather than an architectural dependency.
